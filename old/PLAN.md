## CROSS-PLATFORM APP PACKAGING — goal stated 2026-09-11, not started

User's stated goal, verbatim intent: within "a few days," turn this into a real app running on **Android, Windows, Linux, and macOS**. Explicit constraints: doesn't need to be an "official" polished installer for most platforms; does NOT need the user to spin up a localhost/dev server or any manual setup — should run from essentially one command or one double-click; should be reasonably safe (not a random unsigned installer people have to fight their OS to run). Asked for options to be researched and saved here — **research only below, nothing implemented yet.**

**Researched options (2026-09-11):**

- **Desktop (Windows/Linux/macOS) — recommend Tauri.** Wraps this single HTML file in the OS's own native webview, producing one real binary per platform (.exe / .AppImage / .app) that just runs on double-click — no browser, no localhost, no install wizard required unless one is deliberately built. Tauri bundles are ~2-10MB vs. Electron's ~80-200MB for the same app, uses meaningfully less idle memory, and multiple current (Sept 2026) comparisons call it "the recommended choice for new desktop applications in 2026." Tradeoff: Tauri's build tooling is Rust-based (a Rust toolchain has to be installed to BUILD it, though the output binary needs nothing extra to RUN) — a real but one-time setup cost, not a per-user cost.
  - **Electron** is the fallback if Tauri's Rust toolchain becomes a real blocker — much larger community/tooling maturity, but 10-20x the bundle size for the same result. Only worth it if Tauri specifically causes trouble.
- **Android — recommend Capacitor.** The standard, actively-maintained, free path from a plain HTML/CSS/JS project to a real installable `.apk`: wraps the page in a native Android WebView shell. Produces a real APK the user can sideload (install directly, no Play Store needed) — matches "doesn't need to be super official." Alternative: one-click online HTML→APK converters (e.g. Capsule HTML2APK, html2app) exist for near-zero setup, but that means uploading the game to a third-party service — worth avoiding unless Capacitor itself proves troublesome.
- **Not recommended as the primary path, but worth knowing about**: a PWA (`manifest.json` + a small service worker) would make the game installable straight from a browser on Android AND desktop Chrome/Edge with near-zero extra work — but it fundamentally needs the game reachable at a URL (hosted somewhere), which conflicts with the "no localhost/server setup" requirement as stated. Worth revisiting only if hosting it somewhere stable ever becomes acceptable.

**Recommended path once picked up**: Tauri for Windows/Linux/macOS (one shared build config covers all 3), Capacitor for Android — 2 build pipelines total, both feeding off this exact same `carCrash.html` with no rewrite needed, matching "keep it a single HTML file" from the Notes & Constraints section below. Both produce a locally-runnable artifact (native binary / APK) with no server, no localhost, no ongoing hosting cost.

Sources: [Tauri vs Electron 2026](https://tech-insider.org/tauri-vs-electron-2026/), [Tauri vs Electron vs Neutralino 2026](https://www.pkgpulse.com/guides/tauri-vs-electron-vs-neutralino-desktop-apps-javascript-2026), [Best Desktop App Frameworks 2026](https://www.pkgpulse.com/guides/best-desktop-app-frameworks-2026), [Capacitor HTML5 games](https://dev.to/eonarheim/android-games-with-capacitor-and-javascript-fac), [Capsule HTML2APK](https://capsuleteam.itch.io/capsule-html2apk-html-to-apk-converter)

**Trust/signing follow-up (2026-09-11), answered directly**: every unsigned build from the path above WILL trigger an OS-level "this might not be safe" warning by default — Windows SmartScreen ("Windows protected your PC," defaults to "Don't run"), macOS Gatekeeper ("from an unidentified developer," blocks the double-click), Android ("This type of file can harm your device" on installing an APK outside the Play Store). Linux/.AppImage is the mildest (just needs `chmod +x`, no scare dialog). None of this means the file IS unsafe — these are reputation checks, not malware scans, and ANY brand-new unsigned indie binary triggers them regardless of code quality. Very normal for indie/hobby games (itch.io is full of it), but it will cost some fraction of more cautious players. Mitigations, cheapest to most effort: (1) free — ship via itch.io/GitHub with a README explaining the warning upfront; (2) ~$100-200/yr Windows code-signing cert, softens SmartScreen; (3) $25 one-time Play Store listing, removes Android's warning almost entirely; (4) $99/yr Apple Developer Program + notarization, removes the Gatekeeper block; (5) a PWA install sidesteps this ENTIRELY (goes through the browser's own native install prompt, no separate executable, no OS gatekeeping) — the one place PWA has a real edge over native builds, at the cost of still needing the game hosted at a URL.

**Direct follow-up — a maximally-transparent local-server option**, user's own idea: instead of (or alongside) a compiled binary, give the user a way to run the game themselves via something fully readable/auditable rather than an opaque .exe:
- **Option A (recommended default)** — pure stdlib, zero custom code: `python -m http.server 8000` (one command, using ONLY Python's own standard library — nothing of the dev's to trust beyond the plain-text game file itself), then open `http://localhost:8000/carCrash.html`. Maximum transparency; the tradeoff is requiring Python already installed.
- **Option B** — a tiny `run.py` (~10 lines) that starts the same server AND auto-opens the browser to the right URL, for people who want closer to double-click convenience. Still fully readable in a text editor, just no longer pure-stdlib-only.
- **Option C** — a `.bat`/`.sh` wrapper per OS that calls the same `python -m http.server` command, giving genuine double-click-and-go on each platform while staying plain-text/inspectable (unlike a compiled binary).
Recommended combination: lead with Option A in the instructions (safest, clearest), offer Option C as an optional convenience layer. This is a complementary THIRD distribution path alongside Tauri/Capacitor above — a good "don't trust the .exe? here's the transparent alternative" fallback — not a replacement for it.

**Save-data continuity across app updates — direct requirement, added 2026-09-15, not yet designed**: whichever packaging path is used, updating the app (new .exe/.apk build) must NOT wipe or corrupt the player's existing scores/coins/achievements/etc. Right now everything lives in browser `localStorage` (see `saveAllTimeStats()`), which is fine for the current "open an HTML file" distribution but needs real thought once this becomes a packaged app: Tauri/Electron webviews and Capacitor's Android WebView each have their own persistence quirks across app-version upgrades (storage can be tied to a webview cache that an installer/updater might clear) — needs verifying per platform, not just assumed safe by default.
- [ ] **User ID / cross-device data portability — user's own idea, 2026-09-15**: give each player an ID at first launch; moving to a new device and entering that ID restores their save (overwriting whatever's on the new device). Explicitly floated as a *lightweight* fairness measure, not real anti-cheat — the user's own reasoning: someone could still hand a friend their save/ID, but at least it stops silently having two divergent saves under one identity, and lays groundwork for if/when any online leaderboard or server component gets built later (an ID to check submissions against). Needs real scoping before starting: how the ID is generated/stored, whether the restore is a manual paste-a-code flow or something fancier, whether "overwrite on restore" is really the wanted behavior (vs. e.g. picking the more-progressed save) — flagged as "maybe that's for the future," not asked for now.
